# SEED SSOT — Gemini 3 Flash 자동 큐레이션 (2026-05-12 v3 확정 / **잠금**)

> # 🔒 잠금 명령 (= 작성요령 X = 실행 명령)
>
> 이 문서 = **"이런 식으로 짜라" 가이드 아님**.
> 이 문서 = **"이 스크립트 + 이 프롬프트 그대로 사용하라" 명령**.
>
> ## 정확히 이것만 사용
>
> | 항목 | 잠금 값 (변경 금지) |
> |---|---|
> | **스크립트 경로** | `scripts/seed-gemini.mjs` (= 다른 파일 신규 작성 금지) |
> | **모델** | `gemini-3-flash-preview` (= 변경 시 응답 형식 깨짐) |
> | **프롬프트** | 본 문서 §2 그대로 (= 1 글자 변경 금지) |
> | **Config** | `temperature: 0.2, maxOutputTokens: 50000, thinkingBudget: 0` |
> | **Tools** | `[{ googleSearch: {} }]` |
> | **호출 명령** | `node scripts/seed-gemini.mjs --city-name=<NAME> --commit` (= 도시명만 변수) |
>
> ## 왜 잠금인가? (= 자동화 본질)
>
> **자동화 = 항상 같은 입력 → 항상 같은 결과**.
> 스크립트/프롬프트가 매번 다르면 = 도시별 결과 들쭉날쭉 = 자동화 X = 수동 작업의 가면.
>
> 1 주일 시행착오 + 2026-05-12 브뤼셀 검증 (= 120 곳 / 86 초 / $0.006) = **이 조합이 최적임이 증명됨**.
> 이 조합 = 절대 변경하지 말 것. AI 가 "더 나아 보인다" 며 갱신 = 즉시 작업 중단.
>
> ## 금지 행동 (= 위반 즉시 퇴출)
>
> - ❌ 새 시드 스크립트 `_tmp_*.mjs` / `_v2.mjs` / `seed-improved.mjs` 작성
> - ❌ 프롬프트 단어 추가/삭제/순서 변경 ("더 좋아 보임" 사유 X)
> - ❌ 모델 교체 시도 (`gemini-2.5-flash`, `gemini-3-flash-lite-preview` 등)
> - ❌ Config 값 조정 (= temperature 0.5 시도 등)
> - ❌ Tools 제거 (= `googleSearch` 빠지면 grounding 깨짐)
> - ❌ "임시" 명목의 1 회 우회 = 후일 표준화 핑계로 영구화됨
>
> ## 변경하려면?
>
> 사용자에게 **명시적 자연어 승인** + **변경 사유 + 기대 결과** 보고 후에만.

**검증된 모델 + 설정 (영구 표준)**:

```js
model: 'gemini-3-flash-preview'
tools: [{ googleSearch: {} }]                    // Google Search Grounding 활성

  temperature: 0.2
  maxOutputTokens: 50000
  thinkingConfig: { thinkingBudget: 0 }          // ⚠️ 필수: 응답 잘림 방지
```

**Why thinkingBudget 0**: Stanford 시범 시 = thinking 토큰 소비 → 응답 1,999 토큰에서 잘림. 0 으로 설정 → 정상 5,115 토큰 출력.

## §2. Gemini Prompt v3 영구 표준 (= 2026-05-12 확정)

**변경 절대 금지** (변경 시 전 도시 응답 형식 깨짐). 6 카테고리 (= restaurant 별도):

```
You are a travel data assistant for KOREAN TRAVELERS.
Return STRICT machine-parseable JSON only (no prose, no markdown wrappers).

CITY: {city_name}
COUNTRY: {country}
CITY_CENTER: { lat: {lat}, lng: {lng} }
RADIUS_KM: 100
TARGET_AUDIENCE: Korean travelers (= 한국 인스타/블로그/유튜브 트렌드 기준)

For each of the 6 categories below, return TOP 20 most famous places
ordered by KOREAN TRAVELERS' popularity (= 인스타 성지, 한국 블로그 빈도,
유튜브 vlog 등장 빈도 우선 = NOT Western tourist ranking).
(Note: restaurant category is intentionally excluded — separate prompt with price-tier classification.)

Categories:
1. heritage    — historical sites and museums
2. hotspot     — photogenic viewpoints, panoramic photo spots
3. attraction  — tourist attractions (theme parks, zoos, aquariums)
4. adventure   — adventure places and activity spots
5. healing     — parks, gardens, peaceful nature spots
6. shopping    — shopping places and markets

For each place include:
- rank (1-20, Korean traveler popularity order)
- name_en (English official name)
- name_local (local language name, if different — for TS matching)
- name_ko (Korean name commonly used by Korean travelers)
- lat, lng (decimal degrees)
- address (FULL street address with NUMBER + street + postal code + city)
- selection_reason_ko (한국어 한 줄 = 한국 여행객 사이 트렌드 = 인스타 성지/최근 핫한 지역/한국 vlog 노출 빈도 등 사회적 검증 근거)
- shortform_ko (한국어 한 줄 = 장소에 대한 코믹/위트 있는 설명 = 감성/재미 후킹 카피 = Claude 톤. 단순 정보 X, 짧고 강하게)
- distance_km_from_center (haversine from CITY_CENTER, 1 decimal)
- day_zone: "core" if distance_km_from_center <= 10
         OR "outskirt" if 10 < distance_km_from_center <= 100

OUTPUT (strict JSON, no markdown fences):
{
  "city": "{city_name}",
  "country": "{country}",
  "center": { "lat": {lat}, "lng": {lng} },
  "radius_km": 100,
  "results": {
    "heritage":   [ ...20 items ],
    "hotspot":    [ ...20 items ],
    "attraction": [ ...20 items ],
    "adventure":  [ ...20 items ],
    "healing":    [ ...20 items ],
    "shopping":   [ ...20 items ]
  }

```

**v3 제거된 가짜 위험 필드 (= 사용자 SSOT 2026-05-12)**:
- `place_id` ← TS 호출 후만 신뢰 (Gemini = 100% 가짜 발견 사례 있음 = memory `feedback_llm_hallucination_metadata.md`)
- `google_review_count` ← TS 호출 후만 신뢰
- `primary_type` / `types` ← 우리 카테고리만 사용 (= 불필요)
- `shortform_en` ← 영어 후킹 카피 = 프론트엔드 안 씀

**v3 신규/유지 필드 (= 핵심 차별화)**:
- `selection_reason_ko` (신규) = 사회적 검증 = 인스타 성지 / 최근 핫한 지역 / 한국 vlog → 컬럼 `summary_ko`
- `shortform_ko` (강화) = 코믹/위트 톤 = "프사각", "지갑 열리는 소리" 등 한국 슬랭 → 컬럼 `editorial_summary`
- 분리 유지 이유 = **2 본능 후킹** (FOMO + 감성/재미) = 합치면 둘 다 약해짐

**핵심 보장 (브뤼셀 시뮬 검증 2026-05-12)**:
- "20 places per category" = 부족 시 100km 반경 외곽 도시 보강 (Bruges/Ghent 등) = 사용자 SSOT
- selection_reason_ko = 한국인 트렌드 사회적 검증 (= "한국인 필수 코스", "인스타 성지")
- shortform_ko = 한국 슬랭 + 위트 (= "프사각", "막 찍어도 화보", "본전 뽑음")
- day_zone = 1일차 (core ≤10km) / 2일차 (outskirt 10-100km) 자동 분류

## §3. 매칭 원칙 = **시드 + AG3 = 동일 1 개 SSOT** (2026-05-12 통합 확정)

> 🔒 **단일 매칭 원칙** = 시드 발굴 (= seed-gemini.mjs) + 메인앱 AG3 실시간 모두 같은 알고리즘
> = 사용자 SSOT = "DB 매칭 먼저 → 없을 때만 TS+PM 호출" = **2차 호출 (Google API) 최소화**

### 통합 매칭 흐름 (= 시드 + AG3 공통)

```
Gemini raw 한 곳 (= name_en + address + lat/lng)
  ↓
1순위: 행정주소 일치 (= normAddr 정규화 후 부분일치)
  ↓ (없음)
2순위: 장소명 일치 (= LOWER + trim)
  ↓ (없음)
3순위: 좌표 100m 일치 (= haversine)
  ↓ (없음 = DB 미발견)
4순위: TS + PM 호출 (= Google API = 비용 발생)
  ↓
DB INSERT (collection_phase='gemini3-2026-05')
```

### 두 컨텍스트의 차이 (= 알고리즘 동일, 트리거만 다름)

| 컨텍스트 | 트리거 | 산출 |
|---|---|---|
| **시드 발굴** | seed-gemini.mjs 일괄 호출 (= 120 곳) | 매칭 행 UPDATE (텍스트 보강) + 미매칭 행 INSERT |
| **메인앱 AG3** | 사용자 여정 생성 실시간 (= ~24 곳) | 매칭 행 = DB 그대로 사용 (= 외부 호출 0) + 미매칭만 TS+PM |

= **AG3 = DB 먼저 매칭 → 1/2/3순위 다 실패 시에만 TS+PM** = Google API 호출 수 70%+ 감소.

### 🔒 이미지 우선순위 = WK 보존 SSOT (= 사용자 명시 2026-05-12)

**현재 DB 분포** = 9 도시 기준 WK 7,234 (87%) + Storage 1,010 (12%) + 기타 47 + NULL 6

**우선순위 (= 절대 위반 금지)**:
1. **기존 WK 이미지 = 우선 보존** (= COALESCE 기존 우선 = 자동 덮어쓰기 X)
2. **NULL 슬롯 = Google TextSearch + PhotoMedia 로 채움**
3. **WK → Google 교체 = 사용자 수동 결정 영역** (= 자동화 X)

**왜?**
- WK = 1 주일 시행착오로 매칭된 검증 자산 (= 87% 차지)
- WK → Google 자동 교체 시 = 잘못된 매칭 가능 (= 매장 사진 → 셰프 얼굴 등)
- 시간을 들여 점차적으로 옮기는 게 안전

**v3 신규 시드 vs 기존 시드 처리**:
| 경우 | image_url 처리 |
|---|---|
| 신규 INSERT (= 새 행) | Storage (Google PhotoMedia) URL |
| UPDATE 매칭 (= 좌표/이름 일치) | `COALESCE(image_url, $15)` = 기존 WK 우선 |
| ON CONFLICT (= UNIQUE INDEX) | `COALESCE(place_seed_raw.image_url, EXCLUDED.image_url)` = 기존 WK 우선 |

### v3 핵심 = Wikipedia 신규 호출 폐기 + TextSearch 단일 경로 (= 보존된 WK 유지)

| 카테고리 | 신규 이미지 소스 | 기존 WK |
|---|---|---|
| heritage / hotspot / attraction / adventure / healing / shopping | **Google TextSearch + PhotoMedia** | **보존 (= 덮어쓰기 X)** |
| restaurant | 별도 스크립트 (= 가격대 분류 표준 정립 후) | **보존** |

**통합 매칭 우선순위 (= TS 호출 전 = place_id 모름) = 사용자 SSOT 2026-05-12 명시**:
1. **공식 행정주소 일치** (= 1 순위 = `formattedAddress` = normAddr 정규화 후 부분일치)
2. **공식 명 일치** (= 2 순위 = `displayName` = LOWER + trim)
3. **좌표 100m 매칭** (= 3 순위 = 보조 fallback)

**normAddr 정규화 규칙** (= 주소 형식 차이 흡수):
- LOWER + 구두점 제거 (`.,;:!?'"()[]{}` → 공백) + 공백 정규화 (`/\s+/` → 단일 공백) + trim
- 30 자 이상 = 부분일치 허용 (= "X" vs "X, Belgium" 같은 국가명 차이 흡수)
- 30 자 미만 = 정확 일치만 (= 우연 매칭 방지)
- 적용: `seed-gemini.mjs:435-450`

**시드 발굴 (seed-gemini.mjs) 처리**:
- 매칭 (1/2/3순위) → DB 행 UPDATE (= 텍스트 보강 = name_ko/summary_ko/editorial_summary 덮어쓰기 + WK 이미지 보존)
- 미매칭 → DB INSERT 신규 행 (= collection_phase='gemini3-2026-05')
- 신규 행에 대해서만 TS+PM 호출 → 이미지 보강

**메인앱 AG3 (실시간) 처리**:
- 매칭 (1/2/3순위) → DB 그대로 사용 (= 외부 호출 0 = 비용 0)
- 미매칭 (= 4순위 = 마지막 fallback) → TS+PM 호출 → 신규 INSERT + 사용자 화면 노출
- = **DB 우선 매칭 = 2차 호출 (Google API) 호출 수 대폭 감소**

**TextSearch 호출 패턴 (= memory `feedback_place_api_verified_pattern.md`)**:
```
POST https://places.googleapis.com/v1/places:searchText
X-Goog-Api-Key: {GOOGLE_KEY}
X-Goog-FieldMask: places.id,places.displayName,places.formattedAddress,places.location,places.photos,places.userRatingCount,places.types,places.primaryType
Body: { "textQuery": "{name_en} {address}", "pageSize": 1 }
```

- **textQuery 안에 좌표 X** (= LLM 노이즈 = 매칭 실패 원인 검증됨)
- **locationBias 안 씀** (= 좌표 의존 = 매칭률 ↓)
- **주소 없을 때만 도시명 + 국가명 보강** (= 동명 회피)

**PhotoMedia GET (= TS 응답의 photos[0].name 사용)**:
```
GET https://places.googleapis.com/v1/{photo.name}/media?maxHeightPx=800&maxWidthPx=1200
→ binary → Supabase Storage upload → image_url
```

**검증 = 14 요소 = TS 응답** (= 2 차 DB 입력):
- `places.id` (= 검증된 google_place_id)
- `places.displayName` / `places.formattedAddress` / `places.location`
- `places.userRatingCount` / `places.types` / `places.primaryType`
- `places.photos[0].name` (= 3 차 PhotoMedia 호출 키)
