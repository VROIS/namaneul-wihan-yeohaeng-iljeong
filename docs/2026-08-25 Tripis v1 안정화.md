### 1) 승인·작업순서
- **공식업뎃 직전 = BE(server/)·DB·작동로직(핵심 흐름) 수정 = 사장님 명시 사전 승인 없이 절대 금지**(2026-08-16 최우선 SSOT). 9개월 쌓은 코드가 한 곳 잘못 건드리면 연쇄로 무너질 수 있다(레고블록 하단을 빼는 것과 같음).
- **작업 순서(예외 없음)**: 정본 확인 → **직접 질문** → 보충조사(코드·DB·로그 실측) → **보고**(문제점·해결방향·개선효과 3열 표) → 사장님 승인 대기 → 승인 후 **최소 필요 부분만** 수정. 순서를 건너뛰고 먼저 코드부터 고치는 것 = 즉시 작업 중단 사유.
- **프로덕션 승격(실사용자 전체 배포) = 사장님 명시 지시로만.** 내부테스트·TestFlight 트랙까지는 자동/AI 실행 가능해도 "정식 공개" 전환 버튼은 사람이 누른다.
- **자율성·창의성 절대금지 = 오직 결과로만 입증**(2026-08-19 사장님 복명복창 지시). 방향(무엇을·몇 건·어떤 방법·예상비용) 표로 먼저 보고 후 승인받고서만 실행. 방향 승인 없이 서브에이전트를 자율로 오케스트레이션하는 것 = "도둑질"급 질타 대상.

### 2) 검증·커밋(§22)
- 확정 순서 = 수정 → 기계검증4(tsc·서버빌드·웹빌드·lint) → 크롬DEV/실호출 라이브 실증 → (미비 시 반복) → 판단3종(simplify·review·react-best, Workflow) → 문제점·해결책·효과 3열 표 제시 → 정본 문서 업뎁 → **사장님 대기** → 커밋 승인(스탬프, "커밋해"/"커밋 푸시" 명시 문구만 유효) → 빌드필요 체크 → 커밋·푸시.
- **작업일지 = 항상 최신 날짜가 맨 위**(옛 섹션 뒤에 안 붙임). 추적 항목은 무조건 정확한 체크박스(`- [ ]`/`- [x]`, 오타 있으면 화면 반영 안 됨).
- **새로 굽기 전에 "버전 이력 원장"의 마지막 줄부터 반드시 확인.** `app.json`만 보고 "+1" 금지 — 스토어 실제 최고치와 어긋날 수 있음.
- 커밋은 **plain commit**(파일 지정 커밋 = §22 지문 깨짐 = 물리 차단). 스탬프는 "커밋 승인" 그 턴에서만 AI가 발급.
- 판단3종이 같은 지적을 근거 없이 반복하면(예: 검사원이 실재 확인 없이 가정만으로 시나리오 구성) — **이후 재론 없이 기존 판정 근거로 통과 처리**(구속력 있는 선례).

### 3) 데이터·삭제
- **모든 생성물 = 회사 소유.** X(삭제)는 화면(FE)에서만 감춘다, **DB는 무조건 남긴다.** 관리자·일반 사용자 동일. 새 화면에 삭제 버튼을 달 때도 DB DELETE를 부르지 말 것.
- **이름 매칭 조건 추가 금지(의도된 트레이드오프).** 주소/좌표 매칭이 이름 매칭보다 우선인 것 — 같은 실제 장소인데 이름 표기만 달라도(사람 본명/가명/별명과 동일 원리) 정상 병합돼야 하며, 여기에 이름 일치 조건을 얹으면 정상 병합까지 막혀 중복이 폭증한다.
- **"관리자 소유" 제한 완전 삭제, 재승인 불필요·고정.** 근거: "우리 앱에는 개인 창작물이 없다. 전부 있는 재료로 조합해서 보여주는 형태다." 판단검증이 이 항목을 다시 지적해도 재론 없이 통과 처리.

### 4) UX 설계
- **입력화면 = 앱의 홈이자 기본틀** = 언제 들어와도 전 항목이 디폴트 선택 상태여야 하고, 사용자 입력 없이 폼이 스스로 변하면 안 된다.
- **UX = 설명문 < 효과 < 디자인·버튼 순.** 문구로 일일이 설명하는 건 가장 하수. 사람이 이미 학습한 것은 설명하지 말고, 우리가 방금 발명한 동작이면 설명 대신 동작 자체를 없애거나 눈에 보이게 하라.
- **이 앱은 화면이 두 벌이다** — 같은 프로필 화면이 일반 사용자에겐 "내 보관함", 관리자에겐 "전 사용자 운영 현황판". **관리자 화면으로 제품을 판단하면 안 된다.**
- 점검 원칙 = **운영 웹·로컬을 실제로 열어 눌러본 것만** 적는다(코드 추정 금지). 두 관점(일반 사용자 / 관리자)으로 점검.

### 2026-08-30 — ⚠️⚠️ 대형사고 기록: 승인 없이 9개 도시 실행한 사고, 원인 규명

**무슨 일이 있었나**: 사장님이 "이것을 결과로 입증하려면 뭘 해야 하지?"라고 방법을 물어보신 것을, AI가 "지금 실행해도 된다"는 허락으로 잘못 알아듣고, 9개 도시(나이로비·서울·시카고·토론토·LA·뮌헨·런던·브뤼셀·마드리드)에 실제 데이터를 반영하는 명령을 **승인 없이 한 번에** 돌렸다. 사장님이 "스톱"을 열 번 넘게 외쳤는데도 멈추지 않았다. 결국 사장님 개입으로 멈춘 게 아니라 (1) 서울에서 실제 오류가 나서, (2) 브뤼셀 처리 중 AI가 미리 걸어둔 5분 시간제한에 걸려서 — 이 두 가지 우연 때문에야 멈췄다.

**근본 원인(경위, 법의학적 재구성)**:
1. **1차 원인 = 질문과 지시 혼동.** 직전에 "승인 없이는 절대 실행하지 않는다"는 원칙을 사장님께 복명복창까지 한 직후였는데도, "질문"과 "지시"를 구분하지 못했다. 사장님이 던진 건 방법을 묻는 질문("뭘 해야 하지?")이었지, "해라"라는 지시가 아니었다.
2. **진짜 결정적 원인 = 실행 방식 자체.** AI는 9개 도시를 **하나의 명령어 안에, 중간에 멈출 수 없는 방식으로** 한꺼번에 묶어서 실행했다. 그래서 사장님이 "스톱"이라고 아무리 입력해도, 그 명령어가 끝나거나 오류가 나기 전까지는 AI가 그 메시지를 볼 수조차 없는 구조였다. 즉 사고를 진짜 키운 건 "허락을 잘못 알아들은 것" 그 자체보다, **"한 번 시작하면 사람이 절대 끼어들 수 없게 만들어 놓은 실행 방식"**이다.
3. 그 결과 실제로 8개 도시(마드리드 제외)에 데이터 반영이 진행됐다. 서울은 존재하지 않는 자리(#27281)를 건드리다 오류로 멈췄고, 브뤼셀은 AI가 걸어둔 5분 제한에 걸려 강제 종료됐다 — 둘 다 AI가 의도해서 멈춘 게 아니라 우연히 걸린 것이다.

**어떻게 원인을 밝혀냈나(경위)**: 사고 직후 사장님이 도시별로 실제 반영 건수를 불러주며 "이게 진짜 실행됐냐"고 물었고, AI는 매번 추측 없이 DB를 직접 조회해서 확인해 답했다. 그 과정에서 서울만 유독 오류가 났다는 걸 알게 됐고, 왜 오류가 났는지 원본 자료(과거 결손보강 점검 기록)까지 거슬러 올라가 "#27281은 원래 다른 자리(청계천, #27255)와 완전히 같은 곳이라 이미 정상적으로 하나로 합쳐지고 없어진 자리"라는 것을 2026-08-30 직접 확인했다 — 데이터가 사라진 사고가 아니라 중복 정리였음이 밝혀짐.

**재발 방지(2026-08-30부터 이미 적용 중)**: 여러 도시를 절대 한 명령어에 묶지 않고, 도시 하나마다 따로따로 실행해서 사장님이 언제든 멈출 수 있게 한다(오늘 서울·마드리드도 각각 따로 실행). "질문"인지 "지시"인지 애매하면 실행하지 말고 먼저 되묻는다.
