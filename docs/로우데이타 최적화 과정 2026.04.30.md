## 2. 핵심 SSOT (사용자 정립 2026-04-29 ~ 2026-04-30)

### 2.1 검색은 Google 분류로, 우리 카테고리 X
- 검색 시점 = 장소 누구인지 모름.
- textQuery = **Google 자체 type 자연어**. 우리 7 카테고리 키워드 X.
- 결과 받은 후에야 장소·순위·우리 카테고리 확정.

### 2.2 7 카테고리 textQuery (확정 — 사용자 정정 2026-04-30)

> **원칙**: textQuery = **Google 자체 type 영문 자연어 묶음** (언더스코어 → 스페이스).
> "heritage" 같은 우리 카테고리 추상어는 X. Google API 는 인간이 아니므로 type 명 그대로 자연어 OR 묶음으로 줘야 함.

| 우리 카테고리 | textQuery (type 자연어 묶음) |
|---|---|
| heritage | `museum art museum science museum history museum historical landmark historical place castle monument palace fortress church cathedral mosque temple synagogue archaeological site cultural center in {city}, {state}, {country}` |
| hotspot ⭐ | `viewpoints photo spots in {city}, {state}, {country}` ※ **type 묶음 X — 사용자 검증 단일 SSOT (멕시코시티 8/8)** |
| attraction | `tourist attraction amusement park zoo aquarium theme park planetarium in {city}, {state}, {country}` |
| adventure | `amusement park water park theme park hiking area climbing gym gym sports complex ski resort nature reserve in {city}, {state}, {country}` |
| healing | `park spa garden botanical garden beach wellness center nature preserve in {city}, {state}, {country}` |
| shopping | `shopping mall department store store supermarket market in {city}, {state}, {country}` |
| restaurant | `restaurant cafe bakery bar food meal takeaway meal delivery in {city}, {state}, {country}` |

**규칙**:
- 6 카테고리 (heritage, attraction, adventure, healing, shopping, restaurant) = type 명 그대로 자연어 묶음 (언더스코어 → 스페이스).
- **hotspot 1 카테고리만 예외** = `viewpoints photo spots` (Google 에 viewpoint type 없으므로 사용자 검증된 자연어 단일 SSOT, 다른 표현 X).
- 끝 접미 = `in {city}, {state}, {country}` (state 없는 도시는 도시·국가만).
- 검색어 = `도시 + 주 + 국가` 명시 (메모리 [project_bts_data_insights]).
- pageSize = **10** (사용자 정정 2026-04-30, "구글 뷰어 카운트 순 10 주세요")
- FieldMask = `*` (모든 필드 약 37 개)
- 정렬 = `userRatingCount DESC` (응답 받은 후)

### 2.3 Hotspot 우회 (Google 카테고리 없음 — 단일 SSOT 확정)
- Google API 에 `viewpoint` 또는 `photo_spot` 전용 type **없음** (사용자 직접 실호출 검증).
- Google Maps "카메라 아이콘" = 내부 AI 분석, API 미노출.
- **사용자 검증 단일 SSOT (2026-04-29)**: `viewpoints photo spots in {city}, {state}, {country}` = 인증샷 명소 8/8 정확 반환 (멕시코시티 입증).
- 다른 표현 (예: `observation deck viewpoint scenic overlook ...` 5 type 묶음) = **검증 안 됨, 사용 금지**. textQuery 는 위 자연어 단일.
- 응답에서 `observation_deck`, `cultural_landmark`, `monument`, `plaza` 등이 hotspot 으로 분류 (TYPE_TO_CATEGORIES §3.1).

### 2.4 multi-tag 분류 (types[] 기반)
검색 카테고리 = primary. 응답의 `types[]` 보고 7 카테고리에 추가 매칭 = `category_tags` 배열.

**예 (멕시코시티 검증)**:
| 장소 | Google types | category_tags |
|---|---|---|
| Zócalo | plaza, tourist_attraction, historical_place | hotspot, attraction, heritage |
| Bellas Artes | cultural_center, tourist_attraction, art_museum, museum | hotspot, attraction, heritage |
| Chapultepec Park | park, tourist_attraction | hotspot, healing, attraction |
| Castle | castle, historical_landmark, museum | hotspot, heritage, attraction |

### 2.5 placeId dedup
- 7 카테고리 검색 결과 → `place.id` 로 dedup
- 같은 placeId 가 여러 카테고리에 잡히면 = `category_tags` 에 모든 카테고리 추가
- primary = 첫 잡힌 카테고리 (또는 가장 높은 rank)

### 2.6 도심 100km 거리 필터 (사용자 SSOT, 멕시코시티 검증)
- `cities.latitude` / `cities.longitude` 기준 haversine 100km 이내만 통과
- 100km 초과 응답 = 제외 (silent skip 금지, log 명시)
- 사유: 작은 도시 (Stanford 등) Google API 가 광역 (San Francisco, Monterey 등) 으로 빠지는 결과 자동 차단
- 사용자 메모리 [reference_user_ssot_algorithm]: "6 카테고리 + 검색/리뷰/이미지 3 조건 + 100km"
- 멕시코시티 검증 시 이미 적용됨 (사용자 1주일 SSOT 정립)
- 필터 결과 부족 (예: 카테고리당 < 10) = 사용자 SSOT (작은 도시 한계 인정), 가짜 채우기 X

### 2.7 사진 채움 (PhotoMedia + Storage) — Stanford 검증 후 확정 2026-04-30
- top 10 의 `photos[0].name` 추출
- Google Photo Media API: `GET /v1/{photoName}/media?maxHeightPx=1200&maxWidthPx=1600&key=KEY`
- 받은 binary → Supabase Storage `place-images/{cityId}/{primaryCategory}/{placeId}.jpg`
- 우리 CDN URL = `https://{supabaseUrl}/storage/v1/object/public/place-images/{path}`

#### 2.7.1 한도 SSOT (실측 정정 — Stanford 60 행 검증)
- **GetPhotoMediaRequest per minute per user = 10** (Google Cloud Quota 화면 직접 확인)
- **GetPhotoMediaRequest per minute (project) = 500**
- **GetPhotoMediaRequest per day = 2,000**
- 단일 API key = single user → **분당 10** 한도 적용
- 이전 메모리 "분당 100 안전선" = 잘못된 가정 (실측 17 호출 후 429)

#### 2.7.2 호출 패턴 (Stanford 60 행 7 분 → COMMIT 검증)
1. **Stage 6 시작 전 60 초 init cool down** (직전 실행 슬라이딩 윈도우 빠짐)
2. **호출 간격 = 6,000ms** (분당 10 = per user 한도 정확 부합)
3. **429 발생 시 60 초 대기 후 1 회 retry** (헌법 §6 에러 처리 표 명시)
4. retry 도 실패 = 그 행만 `image_url = NULL` (silent skip 금지, log 명시)

#### 2.7.3 후임 AI 가 한도 변경 시
- per user 한도 상향 (예: 100 으로) = `setTimeout(r, 600)` 으로 환원 가능
- 헌법 §2.7.1 한도 표 갱신 + 스크립트 line 갱신 + 메모리 [feedback_place_api_verified_pattern] 갱신 동시

### 2.8 트랜잭션 원자성 + ON CONFLICT DO UPDATE (사용자 SSOT 정정 2026-04-30)
```
BEGIN
  DELETE FROM place_seed_raw WHERE city_id=$1 AND collection_phase='bts2026'
                                  AND seed_category IN (7 카테고리)
  INSERT INTO place_seed_raw (...) VALUES (...)
  ON CONFLICT (city_id, name_norm) DO UPDATE SET
    category_tags = (DISTINCT 합집합 of 기존 || EXCLUDED),
    phase_tags    = (DISTINCT 합집합),
    image_url     = COALESCE(EXCLUDED.image_url, 기존),
    google_review_count = COALESCE(EXCLUDED.google_review_count, 기존),
    rank = LEAST(기존.rank, EXCLUDED.rank),
    updated_at = NOW()
    -- seed_category (primary), name_en, lat/lng = 기존 유지 (bts_* 메타 우선)
  검증 (헌법 §8.1 카테고리별 multi-tag ≥ 7 + 이미지 ≥ 7)
COMMIT 또는 ROLLBACK
```
- 사유: 글로벌 UNIQUE INDEX `(city_id, name_norm)` 충돌 = bts_* 메타 (선임 보존) 와 새 7 카테고리 응답이 같은 장소 (예: Madrid Bernabéu = bts_venue + hotspot)
- ON CONFLICT DO UPDATE = multi-tag union + 이미지 채움 = 사용자 메모리 [feedback_multitag_ssot] "1 장소 = 1 row, category_tags 배열" 그대로
- batch INSERT 1 행 실패 → 전체 ROLLBACK → 데이터 보존
- v1 손실 사고 (179 → 0) 재발 방지

#### 2.8.1 raw 재사용 (`--reuse-raw` 옵션)
- ROLLBACK 후 정정 + 재실행 시 = 디스크 raw JSON + Storage 이미지 그대로 사용
- Stage 1 (textSearch) skip + Stage 6 (PhotoMedia) skip + Stage 7 (Storage) skip
- Stage 3+4+5 (분류/필터) + Stage 8 (트랜잭션) 만 재실행
- = 약 1 분 (vs 처음부터 7 분)
- 비용 절약 (Google API 호출 0, Storage 업로드 0)

## 4. 워크플로 (8 단계, 도시 1 곳)

```
[1] textSearch 7 카테고리 병렬 (FieldMask=*, pageSize=10)
       ↓
[2] raw JSON 백업 저장 (디버깅·재처리용, _seed_raw/{cityId}_{cat}.json)
       ↓
[3] userRatingCount DESC top 10 추출 (각 카테고리)
       ↓
[4] types[] 분석 → 우리 7 카테고리 multi-tag 분류
       ↓
[5] placeId dedup (검색 카테고리 = primary, types[] 기반 추가 = category_tags)
       ↓
[6] 각 장소 photos[0].name → PhotoMedia API → JPEG binary
    (600ms 간격 강제)
       ↓
[7] Supabase Storage 업로드 → CDN URL 받기
       ↓
[8] 트랜잭션 INSERT/UPDATE
    BEGIN → DELETE → INSERT → 검증 → COMMIT/ROLLBACK
```

**1 도시 호출 합계**:
- textSearch = 7
- PhotoMedia = ~70 (multi-tag dedup 후 실제는 적음, top 10 × 7 카테고리 dedup ≈ 30~50)
- Storage upload = 동수
- 무료 한도 안 (멕시코시티 1 도시 = $0)

## 6. 에러 처리 (실패 패턴 5 가지)

| 패턴 | 원인 | 처리 |
|---|---|---|
| Google API 429 | 분당 한도 초과 | 60 초 대기 → 재시도 1 회 → 도시 skip |
| duplicate key | 같은 name_norm 글로벌 충돌 | 트랜잭션 ROLLBACK → 해당 도시 0 행 (가짜 채우기 X) |

| Storage upload 5xx | Supabase 일시 에러 | 5 초 대기 → 재시도 2 회 → 그 행만 image_url=NULL |

## 8. 검증 통과 기준

> **사용자 SSOT 정정 2026-04-30**: 검증은 **multi-tag (`category_tags`) 기준**으로 카테고리별 카운트.
> 사유: 사용자 2일치 × 하루 5장 = **10장 프론트엔드 노출 기준**. 한 장소가 여러 카테고리에 걸쳐도 "중복 인정".
> 예: Las Vegas healing primary 검색 1 곳 (Google 한계) → multi-tag 10 곳 (다른 카테고리에서 healing type 매칭) ✅

### 8.1 카테고리별 검증 기준 (핵심)

**7 카테고리 모두**에 대해 다음 SQL 통과:
```sql
SELECT cat,
  COUNT(*) FILTER (WHERE category_tags @> ARRAY[cat]) AS multi_total,
  COUNT(*) FILTER (WHERE category_tags @> ARRAY[cat] AND image_url IS NOT NULL) AS multi_with_img
FROM place_seed_raw, unnest(ARRAY['heritage','hotspot','attraction','adventure','healing','shopping','restaurant']) AS cat
WHERE city_id = $1 AND collection_phase = 'bts2026'
GROUP BY cat
```
- **multi_total ≥ 7** (모든 카테고리, 중복 인정)
- **multi_with_img ≥ 7** (이미지 있는 행만 카운트, 프론트엔드 노출 가능)

### 8.2 보조 기준 (전체 합계)

1. 좌표·이름 NULL = 0 (`latitude`, `longitude`, `name_en`)
2. `google_review_count` NULL = 0 (정렬 키)
3. raw JSON 백업 파일 7 개 (`_seed_raw/{cityId}/{cat}.json`)

### 8.3 미달 시 처리
- 트랜잭션 ROLLBACK (기존 데이터 보존)
- 사용자에게 `cat: multi(img)` 카운트 표 보고
- 작은 도시 (예: 자연 자원 부족) = 카테고리 한 곳 미달 가능 → 사용자 결정 (재발굴 / 보존 / 다른 textQuery 시도)

### 11.2 2 차 작업 정의 — `places` 테이블 메인앱 이미지 교체

#### 11.2.1 진단 결과 (사용자 직접 검증 2026-04-30)
- 메인앱 화면 = **이미지 매칭 50%** (사용자 명시)

  - `latitude` / `longitude` = **100% 채움** (좌표 문제 X)
  - `name` = 영문 (예: Bernabéu, Grand Place, Eiffel Tower)
  - `display_name_ko` = **0** (한국어 이름 X)
  - `google_place_id` = **ChIJ... 형식 살아있음** (재호출 가능)

  - = HTTP HEAD 검증 6 표본 = **모두 404**

#### 11.2.2 핵심 원인
- `photo_urls` 의 Google API URL = **API key 첨부 안 됨**

- 사용자 50% 매칭 = 정확

#### 11.2.3 교체 방법 — `google_place_id` 활용
```
1. PlaceDetails API:
   GET /v1/places/{google_place_id}?key={KEY}&X-Goog-FieldMask=photos
   → 새 photos[].name 받음 (만료 X, 새 resource)

2. PhotoMedia API:
   GET /v1/{photoName}/media?maxHeightPx=1200&maxWidthPx=1600&key={KEY}
   → binary

3. Supabase Storage 업로드:
   place-images/places/{google_place_id}.jpg
   → 공개 CDN URL

4. UPDATE places SET photo_urls = $1 WHERE id = $2
   → JSONB 배열 (Storage 공개 URL)
```
