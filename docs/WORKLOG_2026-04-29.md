## 1. 새 시드 발굴 SSOT 4 단계 확립 (오늘의 가장 중요한 결과)

> 이전 안 (sub-agent Sonnet, Wikidata SPARQL 보조, 30 후보, 50/30/20 가중치) = **모두 폐기**.

### Stage 1 — 초기 시드 발굴 (Discovery)
- **API**: Google Places API (New) `places:searchText` (1 호출)
- **textQuery 포맷**: `${category} in ${city}, ${country}` (자연어 핵심)
- **응답**: 20 후보 / 카테고리 (FieldMask: `places.id,places.displayName,places.location,places.userRatingCount,places.photos`)
- **호출 수**: 7 카테고리 × 1 페이지 = **7 textSearch / 도시**
- **취소된 것**: locationBias (= 매칭 실패 원인), 카테고리 키워드 (= 노이즈), 3 페이지 60 후보 (= 과도)

### Stage 2 — Top N 정렬 (대중 유명세 = 일반 여행자 SSOT)
- **정렬 기준**: `userRatingCount` DESC 단일
- **이유**: 대중 유명세 (실제 방문 빈도) = 일반 한국 여행자 앱 본질. Michelin 등 권위 = 비싼·전문가 편향 = **폐기**.
- **N = 10 / 카테고리** (이전 30 = 과도, 여행자 2-3 일 = 8~20 곳 방문 = 70 카드 충분)
- **검색량 / 이미지 수 가중치 폐기**: Google 비공개 + photos.length max 10 cap = 변별력 0

### Stage 3 — 백필 (Place API photo + Storage)
- **대상**: top 5 (식당 top 10) = 카드 진열대 = **Google 사진 의무**
- **방법** (오늘 검증된 1회용 패턴):
  ```
  textQuery = "${name} ${lat},${lng} ${city}, ${state}, ${country}"
  → searchText (locationBias 없음, pageSize:1)
  → photos[0].name → PhotoMedia 다운로드
  → Supabase Storage upload (place-images/{city}/{cat}/{id}.jpg)
  → DB image_url + image_attribution + google_place_id UPDATE
  ```
- **호출 수**: top 5×6 + restaurant top 10 = 40 PhotoMedia / 도시
- **위키 보충 (강한 4 카테고리만)**: rank 6+ 의 attraction/heritage/adventure/hotspot = Wikipedia 무료
- **약한 3 카테고리 (restaurant/healing/shopping)**: rank 6+ 도 Google PhotoMedia (Step 1 의 photoName 재활용 = $0.10 추가)

### Stage 4 — 후처리 (Post-processing)
- **Storage URL 검증**: 업로드된 파일 200 응답 + 진짜 바이너리 확인
- **매칭 5 km 검증**: 응답 좌표 vs 입력 좌표 haversine
- **photos[0] 비면**: silent skip 금지 → 상세 로그 + 사용자 보고 (= 우리 측 textQuery 결함)
- **DB UPDATE 안전장치**: Storage 업로드 성공 후만 DB UPDATE (rollback 안전)
- **재실행 안전**: `x-upsert: true` (Storage), placeId 기반 (DB)
