# 4. 로그인·계정 구조 — ✅ 확정 (2026-08-08)

## 4-1. 인증 = 소셜 3종만 신규 가입. 이메일창은 "이미 있는 내 계정 찾기"

```
신규 가입 ─── 구글 · 카카오 · 애플 3종만
                (제공자가 메일을 인증해 줌 = email_verified 실제 검사 중)

이메일창 ─── 가입 아님. 이미 있는 계정 찾아 들어가기
             관문 2개 = 메일 + 생년월일이 **둘 다** 맞아야 함
             ("생년월일은 비번처럼" 사장님 SSOT)
             없는 메일 → 404 "구글·카카오·애플로 시작해 주세요"
```

**업계 표준과의 관계**: 구글 Identity Platform 은 ①같은 메일이면 오류 내고 앱이 연결 ②인증수단마다 별도 계정 — **둘 다 표준 옵션**. 사장님 방식(②)은 표준에서 벗어나지 않는다.
공통 금지사항은 **"blind email matching"(메일만 보고 잇기)** 뿐이고, 이 앱은 소셜 3종에서 `email_verified` 를 이미 검사(`auth.ts:142/77`, `auth-apple.ts:94`).

**영향받는 실사용자 = 0명**(실측): 생년월일 보유 9명 = 전부 사장님 / 이메일 가입 5명 = 전부 사장님 테스트.

## 4-4. 탈퇴 설계

**기준 = 우리 재료(장소 id)로 만든 것 vs 개인적인 것.** 구분은 이미 DB 에 있음 = `guides.place_id`.

| | 갈리는 기준 | 탈퇴 시 |
|---|---|---|
| 여정 `itineraries` | 전부 우리 재료 조합 | **남김**(FK 없음, `itineraries.ts:32-34`) |
| 영상 `saved_videos` | 여정 기반 | **남김**(FK 없음) |
| 해설 — 우리 장소 | `place_id` **있음** | **남김**(창고에서 남들이 계속 씀) |
| 해설 — 개인 촬영 | `place_id` **NULL** | **6개월 뒤 삭제** + R2 사진 삭제 |

⚠️ **`users` 행을 지우면 안 된다.** `guides.user_id` 가 CASCADE(`credits.ts:34`) 라 창고 해설까지 사라진다. 대신 **개인정보 칸만 비운다**.

```
탈퇴 → account_status='deleted' + deleted_at  (로그인 차단·화면에서 사라짐)
     → 6개월 안에 다시 로그인하면 복구
        ↓ 6개월 후 (매일 04:30 자동 + 관리자 버튼)
     → R2 개인사진 삭제 → guides WHERE place_id IS NULL 삭제 → users 개인정보 칸 비우기
```

정리 함수 1벌 = `server/services/account-cleanup.ts`. 부르는 곳 2군데(스케줄러 · `POST /api/admin/account-cleanup`).

# 5. 삭제 원칙 — 전 화면 공통 (사장님 SSOT 2026-08-08)

> **모든 생성물은 우리 소유다. 화면(FE)에서만 지워지고 DB 는 무조건 남는다. 관리자·일반 사용자 동일.**

**여정은 창작물이 아니다.** 누구나 **우리 재료(장소 데이터)를 도구로 조합해 보는 것**이라, 여러 사용자가 같은 여정을 만드는 게 정상. 개인 자산처럼 취급하면 판단이 전부 틀어진다.

**구현 1벌** = `client/screens/profile/hooks/useHiddenCards.ts` (`@vibetrip_hidden_cards:{계정}` + `cardKey(종류, id)`). 새 화면에 삭제 버튼을 달 때도 **DB DELETE 를 부르지 마라.**
