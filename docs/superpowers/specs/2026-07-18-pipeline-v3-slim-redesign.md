# 파이프라인 v3 슬림 재설계 — 속도 우선 + 매칭 단일화

> 2026-07-18 사장님 SSOT. 실측 확증 기반. 대원칙 = 속도 우선, 불필요·중복·과설계 과감히 도려냄(§0). 오류는 나면 찾아 다시 만듦(방어코드보다 슬림).

## 1. 배경 = 실측으로 확정된 문제 (Phase 1 완료)

여정 생성 Step2(채우기)가 5초→15초로 느려짐(운영). 로컬 직접 실행 `⏱️PERF` 로그로 병목 2개 확정:

| 병목 | 실측 | 원인 |
|---|---|---|
| 🔴 매칭 전체 PSR SELECT (WHERE 없음, 12,936행) | **2,800ms** | 도시무관 매칭(2026-07-09)이 전체 테이블 스캔 |
| 🔴 ① 순차 upsert 루프 (곳마다 await, 곳당 90ms) | **1,435ms** | for + await = 순차 DB 왕복 |

### 근본 = 매칭 이중설계 (§16·§19 위반)
매칭 판정이 **코드(matcher.ts) + DB(트리거) 2벌** 공존. 기준이 달라 "합쳐질 중복이 신규로 생성"되는 사고를 사장님이 이미 목격. + 코드매칭이 전체 후보(12,936행)를 읽어야 해서 SELECT 2,800ms.

## 2. 설계 = 매칭 단일화(트리거) + 코드는 INSERT만

### 핵심 원칙
1. **매칭 판정 = 트리거 1벌만** (단일 SSOT). 트리거는 이미 7단계 불변 + "같은도시 OR 100km" 조건 완비(place-identity.sql).
2. **코드(matcher.ts)의 매칭 판정 완전 제거** → `place-enrich.ts`로 개명, 정규화·채우기 헬퍼만 남김.
3. **코드는 그냥 INSERT 시도** → 트리거가 중복이면 `[중복차단] id=N` 알려줌 → 그 행 흡수(`recoverTriggerDup` 이미 구현됨).
4. **전체 PSR SELECT 제거** → 매칭을 안 하니 후보 명단 불필요 = 2,800ms 증발.
5. **순차 upsert → 트리거 흡수 방식** = 곳마다 INSERT(트리거 워밍 후 27ms/곳, 실측).
6. **재조회(loadSeedRawMap) 최소화** = 슬롯이 place 객체에서 직접(신규 곳 editorialSummary만 place에 실어 재조회 불필요화).
7. **11개 과분할 → 슬림 통합** = Step2 채우기(1,152줄)를 도려내 핵심만(스킬처럼 한 덩어리).

### 트리거 성능 실측 (검증됨)
- 트리거 1회: 콜드 798ms / **워밍 27ms**
- 16곳 INSERT: 첫 곳 콜드 + 15곳×27ms ≈ **~1.2초** (현재 4,235ms보다 훨씬 빠름)

### 매칭 단일화 안전성 실측 (검증됨)
- PID 크로스도시 중복 = 1건(니스↔모나코, 100km 안) = 트리거 100km로 커버
- 코드매칭 제거해도 트리거가 같은 7단계 판정 = 재활용·재과금방지 유지

## 3. 새 흐름 (슬림)

```
[Step2 = 한 덩어리 WF]
1. Gemini 24곳 → PlaceResult 변환
2. 각 곳 INSERT 시도 (매칭판정 없음, 전체SELECT 없음)
     ├ 성공 = 신규 행
     └ 트리거 [중복차단] id=N = 그 행 흡수(재활용 = 이미지·RC·검증값)
3. 신규·흡수 곳 = TS 병렬 호출 → 결과를 슬롯(place)에 직접 입힘 + 그 행 저장
4. 슬롯 빌드 = place 객체에서 직접 (재조회 없음)
```

- **매칭 SELECT 2,800ms 제거** (2번에서 매칭 안 함)
- **순차 upsert 1,435ms → 트리거 흡수 ~1.2초**
- **재조회 17ms 제거 가능** (4번 place 직접)
