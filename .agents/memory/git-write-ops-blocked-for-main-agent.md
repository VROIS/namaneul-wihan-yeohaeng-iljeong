---
name: All git write operations are hard-blocked for main agent, even when handling an assigned project task
description: Explains that git merge/rebase/fetch/lockfile cleanup all fail with "Destructive git operations are not allowed in the main agent" in this workspace, regardless of whether the current turn is "just chatting" or executing an assigned project task.
---

Attempting `git merge`, `git rebase --continue`, or even `git fetch --dry-run` / removing a stray `.git/*.lock` file from the main-agent conversation environment fails with: `Destructive git operations are not allowed in the main agent. Use the project_tasks skill to propose a new background Project Task...`

**Why:** This block is enforced at the sandbox level based on the environment being "main agent," not based on whether a project task has been assigned to that same conversation. Creating a project task and having the user assign it back to "you" (main agent) does NOT grant elevated git permissions — it's still the same restricted environment. Only a genuinely separate isolated task-agent container (a different execution environment entirely) can run these commands, and this project's task-assignment flow does not appear to route to one when the user picks "main agent" as the assignee.

**How to apply:** When a task requires resolving a git divergence/conflict (merge, rebase, force-push, ref surgery), do not assume that filing a project task and being assigned to it yourself unblocks anything — it doesn't. If blocked this way: (1) stop retrying variants of the same git command, (2) leave the working tree in whatever safe/clean state it's already in, (3) clearly tell the user the repo needs manual resolution via Replit's Git pane UI (Pull/Merge/conflict-resolution buttons operate outside this shell sandbox and are not subject to the same block), and (4) if a true isolated task agent (separate container) is available as an assignment option, prefer that over "main agent" for git-surgery tasks.
